# Error Fix Report

**Date:** 2026-09-26 10:05:28
**Error type:** TypeError
**File fixed:** booking_system_backend/requirements.txt (dependency version pin)

## What went wrong

The `fastapi-mcp` library (version 0.4.0) contains a line inside its own code that calls
`Server(self.name, self.description)` — passing two values positionally to the `mcp` library's
`Server` class. In `mcp` version 1.x this was legal. In `mcp` version 2.x, the `Server` class
was redesigned to accept only **one** positional argument (`name`); `description` was removed
entirely. Because `requirements.txt` did not pin a version for `mcp`, pip installed the latest
(`2.2.0`), which broke `FastApiMCP` on startup.

## The analogy

Think of ordering at a café where you say "one large mocha" — two words in a specific order.
The café retrains their staff and now requires you to say "one coffee, size=large" using
labels. If you still say "one large mocha" the old way, the new staff gets confused.
`fastapi-mcp` was the customer still saying "one large mocha"; `mcp 2.x` was the newly
retrained staff. Pinning `mcp<2.0` keeps the compatible staff behind the counter.

## Fix applied

**File:** `booking_system_backend/requirements.txt`

Before:
```
fastapi-mcp
```

After:
```
fastapi-mcp
mcp<2.0
```

The `mcp` package was then downgraded in the virtual environment from `2.2.0` to `1.30.0`
(the latest 1.x release) by running:
```
venv/bin/pip install "mcp<2.0"
```

## Test added

**File:** `booking_system_backend/tests/test_rest.py`
**Class:** `TestMcpServerInit`
**Function:** `test_fastapi_mcp_server_initialises_without_error`

The test imports `server` (which triggers `FastApiMCP(app)`) and asserts it succeeds without
raising a `TypeError`. It also checks the installed `mcp` major version is less than 2, so any
future accidental upgrade is caught immediately with a clear message.
